# HookBuoy

Local webhook signing and replay for payment integration tests.

HookBuoy sends synthetic Circle Wallets-shaped notifications to a local HTTP handler using a test key you control. Save a signed delivery and replay the same body bytes and signature to exercise your handler's duplicate-delivery behavior.

**Status:** HookBuoy v0.2.0. The 0.x interface and fixture templates remain experimental. HookBuoy is an independent project and is not affiliated with Circle. Its requests are **not signed by Circle**.

## Why HookBuoy?

Use it when you need a small, local loop for testing Circle Wallets-style signature verification and duplicate handling. A raw `curl` request does not create the test signature or preserve a signed delivery for replay; Stripe CLI targets Stripe, while Hookdeck provides a broader webhook development platform. HookBuoy is scoped to locally signed fixtures and replay.

## Requirements and installation

Node.js 22 or newer and npm are required. **HookBuoy is published on npm**:

```sh
npm install --global hookbuoy
hookbuoy --version
hookbuoy --help
```

For a one-off run without global installation, use `npx --yes --package=hookbuoy hookbuoy --help`. To build from source instead:

```sh
git clone https://github.com/NothernZhongKui/hookbuoy.git
cd hookbuoy
npm ci
npm run build
node dist/src/cli.js --help
```

The commands below use `hookbuoy` from npm. In a source checkout, substitute `node dist/src/cli.js`.

## Quickstart

First, run a **local receiver that explicitly trusts test keys**. The included example receiver needs a public key generated by HookBuoy:

```sh
mkdir hookbuoy-demo && cd hookbuoy-demo
hookbuoy keygen --out .hookbuoy
```

In the HookBuoy source checkout, the example receiver can be started with:

```sh
node examples/local-receiver.mjs /absolute/path/to/hookbuoy-demo/.hookbuoy/public.pem
```

Or copy the receiver from the published package's [example source](examples/local-receiver.mjs). The receiver listens only on loopback. From the demo directory in another terminal:

```sh
hookbuoy init --to http://127.0.0.1:3917/api/circle/webhook
hookbuoy send inbound.complete
hookbuoy replay last --times 3
hookbuoy check signature
hookbuoy check body
```

`init` reuses the complete local test key pair. Expect HTTP 200 for valid sends/replays and HTTP 403 for negative cases. The example receiver reports one `NEW` and three `DUPLICATE` observations (plus rejected bad signatures); this demonstrates only the receiver's in-memory test state.

## v0.2 — fewer flags

v0.2 adds an optional local project configuration, a concise numbered terminal menu and negative-signature checks. Existing v0.1 commands remain supported.

```sh
hookbuoy init --to http://127.0.0.1:3917/api/circle/webhook
hookbuoy status
hookbuoy events
hookbuoy send inbound.complete
hookbuoy replay last --times 3
```

For the pinned Arc Commerce local pilot, `init arc-commerce` uses the default `http://127.0.0.1:3000/api/circle/webhook` endpoint. It does **not** patch or start that application, create test purchases, or bypass signature verification. Explicitly configure the receiving app to trust your local public key in an isolated development environment.

`init` creates `.hookbuoy/config.json` and local P-256 test keys (or reuses an existing complete pair). It never silently overwrites configuration or keys. Once configured, each `send` automatically saves a unique, immutable signed request before HTTP delivery under `.hookbuoy/deliveries/`; `replay last` sends exactly that stored request. Pass `--to` to override the saved endpoint, or `--save` to pick a delivery filename.

Run `hookbuoy` in a terminal for a numbered menu: **1** send, **2** replay last, **3** check invalid signature, **4** browse events, **5** status, **6** initialize and **0** exit. Slash commands like `/events` still work. In scripts and CI, no TTY means it prints help and exits, never blocking for input. This is not an AI agent and makes no external API calls.

### Negative-signature tests

Use a locally configured project and running test receiver that checks signatures:

```sh
node dist/src/cli.js check signature           # send invalid signature, expect HTTP 403
node dist/src/cli.js check body                # modify signed JSON body, expect HTTP 403
node dist/src/cli.js send inbound.complete --fault signature --expect-status 403
```

Faults are applied **after signing**, never to the original request object. `signature` flips a bit in the signature while keeping the original body; `body` changes the synthetic `notification.state` while retaining its original signature. Both default to expecting HTTP 403 (override `--expect-status` if your handler rejects with a different status). Exit code 0 means the expected HTTP response was observed, **not** that downstream payment state was audited. When a project is configured, faulted requests are also stored under immutable filenames; `replay last` reproduces the exact faulted request. No Circle-managed keys or remote endpoints are involved.

## Use your handler

Configure your local handler to explicitly trust `.hookbuoy/public.pem` for key ID `hookbuoy-local-test` **only in an isolated test environment**. Preserve its signature verification and verify the original request body bytes before processing the event.

Point `--to` at your local endpoint. The accepted destinations are HTTP `localhost`, `127.0.0.1` and `[::1]`; redirects are not followed. No tunnel or Circle credentials are needed for HookBuoy itself. Your application may have additional requirements.

Two fixture aliases are available: `wallets.inbound.complete` and `wallets.inbound.failed`. Both use `notificationType: transactions.inbound`, with different synthetic states. They are illustrative templates, not complete or authoritative Circle schemas. See [compatibility](docs/compatibility.md) for identifier behavior, signing and limitations.

To exercise an application path that matches an existing local test transaction, supply its hash:

```sh
node dist/src/cli.js send wallets.inbound.complete \
  --to http://127.0.0.1:3000/api/circle/webhook \
  --tx-hash 0x1111111111111111111111111111111111111111111111111111111111111111 \
  --notification-id my-test-event \
  --transaction-id my-test-transaction \
  --save purchase.delivery.json
```

Replace the hash with the value in your test database. IDs can also be omitted to generate UUIDs. The example receiver does not use a database.

`--save` creates a new delivery file **before** the HTTP attempt and refuses to overwrite an existing file. The file remains available even if the HTTP delivery fails. It stores the original body as base64 plus the content type, local key ID and signature; it does not store the private key or destination. `replay` sends the stored body and those headers sequentially without re-signing. The file may contain sensitive test payload data; keep it private.

## HTTP results

By default, any 2xx response is expected. Use `--expect-status 403` to test for a specific status; `--timeout-ms` defaults to 3000 ms.

| Exit code | Meaning |
| --- | --- |
| `0` | All responses matched the expected status. |
| `2` | Invalid input, key, delivery file or file operation. |
| `3` | At least one unexpected HTTP status, with no transport error. |
| `4` | At least one connection or timeout error. |

An expected HTTP response does **not** prove a payment was matched, settled or credited exactly once. Inspect your application's state separately. See the [Arc Commerce pilot](examples/arc-commerce/README.md) for a concrete integration procedure.

## Security and scope

The generated P-256 key pair belongs to you. A receiver using Circle's normal public-key lookup will not trust it unless explicitly configured to do so for local testing. Keep the private key out of version control; never enable local test-key trust in a production deployment or disable signature verification there.

HookBuoy does not create payments, fetch Circle keys, send to remote endpoints, simulate Circle's delivery schedule, or verify ledger and business outcomes. Replay is an intentional sequence of repeated requests, not an automatic retry policy.

## Development

```sh
npm test
npm run smoke:package
```

The package smoke test builds an npm tarball, installs it in a temporary isolated directory without developer dependencies, and verifies the installed CLI, local signed delivery, three byte-exact replays, and invalid-signature rejection. A green source test alone does not establish that an installed package works.
